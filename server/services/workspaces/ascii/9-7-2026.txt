## 1. Workspace

The workspace is the shared state passed through the system.

```text
Workspace
├── workspace details
├── current quiz
├── quiz answers
├── quiz results
├── artifacts
├── tasks
└── interviews
```

`buildWorkspaceContext(workspaceId)` loads all of this data:

[build-workspace-context.js](/home/akash/projects/idea-validator/server/services/workspaces/build-workspace-context.js:3)

The resulting object is consumed by both the orchestrator and individual agents.

```text
workspaceId
    │
    ▼
buildWorkspaceContext()
    │
    ▼
{
  workspace,
  quiz,
  answers,
  results,
  artifacts,
  tasks,
  interviews
}
```


Definition:

[validate-startup.js](/home/akash/projects/idea-validator/server/goals/validate-startup.js:1)

Registry access is wrapped by:

[goals/service.js](/home/akash/projects/idea-validator/server/goals/service.js:1)

A goal does not run code itself. It gives the orchestrator a desired artifact state.

```text
Goal
  "I need these artifact types"
                │
                ▼
Orchestrator
  "Which ones already exist?"
  "Which agents can create the missing ones?"
```

## 3. Orchestrator

The orchestrator converts a goal into agent executions.

Main entry point:

[orchestrate-goal.js](/home/akash/projects/idea-validator/server/services/orchestrator/orchestrate-goal.js:9)

```text
orchestrateGoal(workspaceId, goalName)
    │
    ├── getGoal(goalName)
    │
    ├── buildWorkspaceContext(workspaceId)
    │
    ├── buildExecutionPlan(goal, workspaceContext)
    │
    ├── runAgent(...) for each planned agent
    │
    └── return
         ├── goal
         ├── plan
         ├── knowledge
         └── results
```

Execution planning happens here:

[build-execution-plan.js](/home/akash/projects/idea-validator/server/services/orchestrator/build-execution-plan.js:4)

```text
Goal requirements
        +
Workspace artifacts
        │
        ▼
resolveWorkspaceKnowledge()
        │
        ├── existing artifact types
        └── missing artifact types
                    │
                    ▼
             resolveAgentPlan()
                    │
                    ▼
          ordered list of agents
```

Workspace artifact resolution:

[resolve-workspace-knowledge.js](/home/akash/projects/idea-validator/server/services/orchestrator/resolve-workspace-knowledge.js:3)

Agent dependency resolution:

[resolve-agent-plan.js](/home/akash/projects/idea-validator/server/services/orchestrator/resolve-agent-plan.js:6)

The planner recursively asks:

```text
Missing artifact
      │
      ▼
Find agent that produces it
      │
      ▼
Does that agent require other artifacts?
      │
      ├── yes → resolve those first
      └── no  → add agent to execution plan
```

If multiple agents produce an artifact, `chooseBestProducer()` currently selects the first one. There is no scoring or routing logic yet.

## Current Gaps

The architecture is present, but the registries do not yet agree with each other:

```text
Goal requires
├── customer-pain          missing definition
├── market-opportunity     missing definition
└── major-risk             missing definition

Research agent requires
└── customer-persona       missing definition and producer
```

This causes `validate-startup` planning to fail around `resolveAgentPlan()`: the only available agent requires `customer-persona`, but no registered agent can produce it.

Tools have a similar gap:

```text
Research agent declares:
google-search + browser + rss

Active tool registry contains:
calculator

Agent execution tool loop:
not implemented
```

So the current repo has a solid architecture skeleton:

```text
Goal → Orchestrator → Agent → Artifacts → Workspace
                         │
                         └── Tools (planned, not wired)
```

But the immediate runnable state is closer to:

```text
Direct research agent run → LLM → validated artifacts/tasks → database
```

The goal-driven, dependency-planned, tool-using multi-agent system is only partially connected.
